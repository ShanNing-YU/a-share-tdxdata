# 单只拉取 4s 延迟根因调查（2026-09-18）

## 现象
- 旧 pytdx 时代全服务器 2721 只尾盘 5min ~2-3 分钟拉完（用户记忆）
- 新 tdxdata 单连接单只 bars **固定 ~4.0s** → 全池 5196 只：43 并发 537s/9 分钟，100 并发 236s/4 分钟
- 用户提出：模仿旧 pytdx 的请求头提速（非高并发）

## 实测对照（同服务器 101.35.121.35）
| 客户端 | 单只 bars | 返回 | 说明 |
|---|---|---|---|
| pytdx(旧 0x01016408) | **41ms** | 0 根 | 服务器对旧版本头**直接拒**（返回空），不是真快 |
| tdxdata(新 0x01007b18) | **4.05s** | 5 根 | 服务器对新版 K 线请求 **per-connection 限速 ~4s/请求** |

## 结论（根因）
- **pytdx "2-3 分钟快" = 旧服务器不设限速**：41ms/只 × 2721 只 × 单连接串行 ≈ 112s ≈ 2 分钟。不是"请求头好"，是旧服务器协议没折旧判官。
- **tdxdata 4s/只 = 服务器对新版单请求限速**（每连接每请求 ~4s）。这是服务器端策略，改客户端请求头无用——pytdx 的老头已被服务器识别为「旧版本」而拒（返 0 根）。
- **单连接被限速 ~4s → 提速只能靠并发更多连接**（每连接独立限速，并发即摊薄）。43 个 IP 已全用（100 并发复用），达服务器并发上限；再提有拉黑风险（analysis_round 曾记录）。

## 当前最优
- 100 并发 → 全池 5196 只尾盘 = **236s（4 分钟）**，每秒 ~22 只
- 想再快只能：a) 0c01 加密会话(批量不限速) — 用户红线不研究；b) 换数据源

## 关键结论（勿再走弯路）
**不要模仿 pytdx 请求头** —— 那是服务器已拒绝的旧版本标识，模仿反而失效（返 0）。服务器对新格式单请求设 ~4s 限速，属服务端策略不可协商；提速只能是并发连接数（已达顶）。
