# 通达信协议逆向分析报告（第一轮，2026-09-14）

## 结论（中期）
1. **协议框架未变**：TCP 7709 端口仍用老命令族（0x01/0x02/0x03 + 请求-响应头），pytdx/xmtdx 的结构解析可用
2. **老库全空根因**：通达信新版客户端改用**推送式行情**——连接后服务器用**固定 74B 段持续推送**（同一股票快照重复推送），不再响应老式「拉取请求」；且**载荷高熵（疑似加密/zlib 流式压缩跨段）**
3. **加密未逆出**：74B 段内 0x16 偏移有 `78 9c`（zlib 头），单段解压 0 字节、跨段拼接失败——可能是跨段 zlib 或 Xor/RC4 加密，需进一步分析

## 关键抓包证据
- 8225 服务器→客户端载荷，最大流 7788 包，**段长 74B 占 7542 个**
- 请求变体（客户端→7709）：
  - `0000000000007c05` x1290（心跳/长度帧）
  - `0c01187b00011a01...` x6（K线请求，版本字段 18 7b 00 01 vs 老 08 64 01 01）
  - `0c02080007013601` x18 / `0c01080007003601` x12（其他命令）
- 服务器 IP：175.178.128.227（18 连）、124.71.137.253、123.60.102.110 等（腾讯云段）
- 通达信客户端还连内网 IP 10.37.35.70 的 40279/44911/37393/59437 端口（未知用途，可能是本地代理/推送）

## 已尝试
| 方法 | 结果 |
|---|---|
| 原版 pytdx 格式请求 → 服务器 | 0 字节响应 |
| 修改版本字段（18 7b 00 01）→ 服务器 | 0 字节/超时/断连 |

B. **等社区**：easy_tdx（clong365）2026-05 还在活跃，可能已关注协议改动；xmtdx 作者可能更新

## 现实评估
- 若为流式加密推送：逆向 1-3 天，成功后可恢复「高速批量」；若每日换 key 则不可行
- 现用 HTTP 体系（四源轮换 + 快照补当日）已能覆盖需求，逆向是「锦上添花」
